# 交通出行法规 RAG 智能问答系统 · 项目介绍

## 一、项目目标与用途

本项目是一个**完全本地运行**的垂直领域检索增强生成（RAG）问答系统，面向中国交通出行法规场景。

用户以自然语言提问，系统从自建法规知识库中检索相关条款，组装带编号引用的提示词，交由本地大模型生成**可溯源**的回答——每个关键结论都标注来源编号，点击即可定位到具体法规条款。

### 解决的核心问题

通用大模型回答法规类问题时存在三个典型缺陷：

| 问题 | 表现 | 本项目的应对 |
| --- | --- | --- |
| 幻觉 | 编造条款号、记分分值、罚款金额 | 强制只用检索片段作答，信息不足时明确拒答 |
| 不可溯源 | 无法判断答案是依据哪条法规 | 每个结论强制标注 `[1]` `[2]`，右侧栏展示原文出处 |
| 领域漂移 | 对任何话题都"乐于回答" | 话题边界守卫拦截离题提问，引导回业务范围 |

### 业务范围

覆盖 **14 个类别、94 条法规知识**，横跨五类出行方式：

- **道路交通**：信号灯与通行、限速、酒驾毒驾、驾驶证记分、让行优先、停车管理、事故处理、违法处罚、行人非机动车
- **高速公路**：通行规则、限速、应急车道、故障处置
- **铁路高铁**：禁烟、携带品、票务、安检
- **城市轨道交通**：票务、安检、站台安全
- **民用航空**：锂电池与充电宝、行李、值机、无人机管理

所有数据依据《道路交通安全法》及其实施条例、《道路交通安全违法行为记分管理办法》（公安部令第 163 号）、《铁路安全管理条例》《城市轨道交通运营管理规定》《民用航空法》等公开法规整理，每条均标注条款出处。

> **免责声明**：本项目用于技术学习与参考，不构成法律意见。具体执法以主管部门认定及官方最新文本为准。

## 二、核心功能

### 2.1 检索增强问答

- **混合检索**：向量语义召回 + 关键词前置召回，取并集后统一打分，解决中文短问句向量区分度不足的问题
- **二次精排**：综合语义分、关键词命中率、标题精确命中三重信号重排，把跨领域提问的正确条款顶到 Top-1
- **多重过滤**：相似度阈值过滤、同源限流（同一条法规最多 2 个片段）、字符 2-gram 去重

### 2.2 三版本提示词工程

内置 v1（朴素）/ v2（角色）/ v3（严谨）三套 Prompt，便于做效果对照。默认 v3，其关键约束：

- 只使用检索片段中的信息，禁止凭记忆编造数字与条款
- 每个关键结论后标注来源编号 `[n]`
- 片段确实无关时才说"根据现有知识库无法确认"，有依据则必须作答
- 禁止提供规避执法类建议

### 2.3 回答详细程度自适应

按问题类型自动分三档，并同步调整生成长度上限：

| 档位 | 触发条件 | 生成上限 |
| --- | --- | --- |
| concise | 直接事实查询（扣几分 / 罚多少 / 能不能） | 160 tokens |
| standard | 一般法规问答（默认） | 384 tokens |
| detailed | 情形分析、流程步骤（怎么办 / 怎么区分 / 我该怎么办） | 640 tokens |

### 2.4 话题边界守卫

用**确定性术语词表 + 会话上下文**判定提问是否属于交通出行领域，五级短路判定：

1. 命中交通领域术语 → 放行
2. 命中其他领域主题词 → 拦截（优先于多轮放行，防止话题突变）
3. 检索 Top-1 关键词命中率 ≥ 0.30 → 放行（词表遗漏兜底）
4. 有历史且确实像追问（含"那/呢/再"等承接词且 ≤24 字）→ 放行
5. 其余 → 拦截

拦截时直接返回预写的委婉引导语，**不调用大模型**（实测 0.1 秒内返回，正常生成需数秒），且该轮不写入会话历史，避免污染后续多轮判定。

### 2.5 可打断的流式生成

生成过程中输入框**全程可用**，支持两种打断方式：

- 点「停止生成」→ 中止当前流，保留已生成内容
- 直接输入新问题发送 → 中断旧回答，立即开始新一轮

打断在**三层协同**生效：前端 `AbortController` 中止 SSE、Flask 每会话一个 `threading.Event`、Ollama 封装每次收 token 前检查标记并关闭连接——后端推理真正停止，而非仅前端停止显示。

### 2.6 多轮对话

- **指代消解**：对"那罚款呢？"这类追问，融合上一轮主题词后再检索；若当前问题已含强主题词（如"那高铁呢"），则判定为自足不融合，避免主题被污染
- **历史管理**：只保留最近 5 轮，历史回答截断至结论前缀，控制上下文膨胀
- **会话持久化**：历史落盘到 JSON 文件，重启服务不丢失，带 TTL 过期与超量淘汰

### 2.7 工程化防护

| 能力 | 实现 |
| --- | --- |
| 限流 | 令牌桶（惰性补充，默认 1 token/s、容量 5），按会话 ID 或 IP 计 |
| 输入长度 | 上限 500 字符，防止超长问题拖垮嵌入与生成 |
| 访问日志 | 记录时间、客户端、路径、状态码、耗时，同时输出到 stdout 与文件 |
| 健康检查 | `/api/health` 汇总 Ollama 嵌入、生成、向量库三项状态 |

## 三、技术架构与主要模块

### 3.1 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 大模型运行时 | Ollama | 本地 HTTP 服务，无需联网推理 |
| 嵌入模型 | `nomic-embed-text` | 768 维，中英文语义向量 |
| 生成模型 | `qwen2.5:1.5b`（默认） | 可切 3b / 7b，通过环境变量一键替换 |
| 向量数据库 | LanceDB | 本地持久化，支持 cosine 度量与相似度检索 |
| Web 框架 | Flask 3.x | SSE 流式响应（`stream_with_context`） |
| 前端 | 原生 HTML / CSS / JS | 无框架依赖，SSE + AbortController |
| 测试 | pytest | 38 项，绝大多数不依赖 Ollama |

### 3.2 请求链路

```
用户提问
  │
  ├─ Flask /api/chat ──────────────── 参数校验、限流、取会话历史
  │
  ├─ 指代消解（rag/pipeline）───────── 追问时融合上轮主题
  │
  ├─ Ollama 嵌入（rag/embedder）────── 问题 → 768 维向量
  │
  ├─ LanceDB 混合检索（vector_store）
  │    语义召回 → 关键词前置召回 → 融合打分 → 阈值过滤
  │    → 同源限流 → 2-gram 去重 → 二次精排 → Top-5
  │
  ├─ 话题守卫（rag/guard）──────────── 离题 → 直接返回引导语（零大模型调用）
  │
  ├─ 详细程度判定（rag/verbosity）──── concise / standard / detailed
  │
  ├─ 构造 Prompt（rag/prompts）─────── 三版本模板 + 编号上下文
  │
  ├─ Ollama 流式生成（rag/llm）─────── 每 token 检查 should_stop
  │
  └─ SSE 事件流 ───────────────────── status / sources / token / stopped / done
        │
        └─ 前端打字机渲染 + 来源侧栏 + 引用跳转
```

### 3.3 主要模块职责

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 配置中心 | `config.py` | 集中管理模型、路径、检索、守卫、会话、防护参数，全部支持环境变量覆盖，便于 dev/prod 切换 |
| 知识加载 | `knowledge_base/loader.py` | 校验字段完整性、按句子边界分段（500 字符 / 80 重叠）、保留溯源元数据 |
| 向量检索 | `knowledge_base/vector_store.py` | 建库、混合检索、融合打分、同源限流、去重、二次精排 |
| 嵌入封装 | `rag/embedder.py` | 兼容新版 `/api/embed` 批量接口与旧版 `/api/embeddings` 逐条接口 |
| 生成封装 | `rag/llm.py` | 流式/非流式生成，`should_stop` 回调实现真正中断，错误分类友好提示 |
| 提示词 | `rag/prompts.py` | 三版本模板、上下文格式化、历史轮次截断，构造 chat messages |
| 话题守卫 | `rag/guard.py` | 领域术语表、离题词表、追问判定、委婉引导话术差异化选取 |
| 详细程度 | `rag/verbosity.py` | 三档判定与对应篇幅指令、token 上限 |
| 流程编排 | `rag/pipeline.py` | 串联检索与生成，输出结构化事件流，同步/流式双入口 |
| Web 服务 | `app.py` | 路由、SSE、中断控制、会话接入、限流与日志 |
| 会话存储 | `session_store.py` | JSON 文件持久化，原子写入、TTL 过期、超量淘汰、损坏降级 |
| 接口防护 | `rate_limit.py` | 令牌桶限流器 + 访问日志记录器 |

## 五、运行方式

### 5.1 环境要求

- Python 3.8+（推荐 3.10+，已验证 3.13）
- Ollama 已安装并启动
- 可用内存 ≥ 4GB（生成模型约 1GB）

### 5.2 四步启动

```bash
# 1) 安装依赖
cd traffic-law-rag
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux
pip install -r requirements.txt

# 2) 启动 Ollama（另开终端）
ollama serve

# 3) 拉取模型并构建向量库
python scripts/pull_models.py
python scripts/build_knowledge_base.py

# 4) 启动服务
python app.py
```

访问 <http://127.0.0.1:5000> 即可使用。

### 5.3 环境自检

```bash
python scripts/check_env.py
```

依次检查 Python 版本、依赖包、Ollama 服务与模型、知识库与向量库，缺失项会给出具体修复命令。

### 5.4 常用接口

```bash
# 健康检查
curl http://127.0.0.1:5000/api/health

# 同步问答（便于脚本测试）
curl -X POST http://127.0.0.1:5000/api/chat/sync \
     -H "Content-Type: application/json" \
     -d '{"question":"闯红灯扣几分？"}'

# 清空会话上下文
curl -X POST http://127.0.0.1:5000/api/clear -H "Content-Type: application/json" -d '{}'
```

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/` | GET | 问答页面 |
| `/api/health` | GET | 环境健康检查 |
| `/api/knowledge/stats` | GET | 知识库统计 |
| `/api/chat` | POST | SSE 流式问答（主流程） |
| `/api/chat/sync` | POST | 同步问答（测试用） |
| `/api/stop` | POST | 中断当前生成 |
| `/api/clear` | POST | 清空会话上下文 |

### 5.5 关键环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `OLLAMA_LLM_MODEL` | `qwen2.5:1.5b` | 生成模型，切换无需重建向量库 |
| `OLLAMA_EMBED_MODEL` | `nomic-embed-text` | 嵌入模型，**更换后必须重建向量库** |
| `OLLAMA_NUM_GPU` | `-1` | GPU 卸载层数，`0` 为纯 CPU |
| `GUARD_ENABLED` | `1` | 话题守卫开关，`0` 关闭（效果对照用） |
| `RERANK_ENABLED` | `1` | 二次精排开关 |
| `FLASK_PORT` | `5000` | 服务端口 |
| `FLASK_DEBUG` | `1` | 调试模式，**生产环境必须设为 0** |

### 5.6 测试

```bash
pytest tests/ -v
```

38 项测试，覆盖知识库完整性、分段与重叠、Prompt 约束、多轮消息构造、去重与精排、会话持久化、限流、话题守卫、离题短路、中途打断等。检测到本机 Ollama 可用且向量库已构建时，自动追加端到端问答测试。

## 六、适用场景

### 6.1 直接适用

| 场景 | 说明 |
| --- | --- |
| 领域问答原型 | RAG 全流程的最小可运行范本，覆盖嵌入、检索、Prompt、生成、流式交互完整链路 |
| 领域问答原型 | 更换知识库 JSON 即可迁移到其他法规、制度、手册类场景 |
| 内网/离线问答 | 全链路本地运行，数据不出内网，适合对数据保密有要求的单位 |
| 法规自助查询 | 出行前查携带品规定、违章后查处罚标准、事故后查处理流程 |

### 6.2 迁移到其他领域

系统的领域相关性集中在两处，替换成本低：

1. **知识库** `data/traffic_law_knowledge.json` —— 按相同字段结构（`id / category / title / content / source / tags`）写入新领域知识，重建向量库即可
2. **话题词表** `rag/guard.py` 的 `DOMAIN_TERMS` 与 `OFF_TOPIC_TERMS` —— 替换为新领域的术语与离题词

其余检索、编排、交互逻辑与领域无关，可直接复用。适合迁移的方向：医疗就诊规范、企业内部制度、产品手册与技术文档、金融合规条款等。

### 6.3 不适用场景

- **需要法律效力认定的正式咨询** —— 系统仅作参考，最终须以主管部门认定和官方文本为准
- **高并发对外服务** —— 当前为单机版，会话存本地 JSON、限流在进程内存，多实例部署需改 Redis 与共享状态
- **超大规模知识库** —— 关键词前置召回采用全量扫描，百级条目代价可忽略，万级以上需改为倒排索引

## 七、已知限制

1. **知识覆盖有限**：94 条为示范规模，法规修订（如 2022 年记分规则调整）后需人工更新并重建向量库
2. **守卫基于规则词表**：边界问法可能误判，生产环境建议改为意图分类模型并保留人工反馈入口
3. **小模型幻觉风险**：`qwen2.5:1.5b` 在检索依据充分时表现稳定，复杂情形仍可能偏离，可通过切换 3b/7b 缓解
4. **单机架构**：会话与限流状态在进程内，水平扩展需引入外部存储
